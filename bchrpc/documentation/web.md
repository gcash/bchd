# Web

It is currently impossible to implement the HTTP/2 gRPC spec3 in the browser, as there is simply no browser API with enough fine-grained control over the requests. For example: there is no way to force the use of HTTP/2, and even if there was, raw HTTP/2 frames are inaccessible in browsers.

For this reason the gRPC team developed [gRPC-Web](https://github.com/grpc/grpc-web) which uses a modified gRPC compatible with browsers.

Traditionally using gRPC-Web requires running a proxy server that translates between gRPC and gRPC-Web,
however BCHD multiplexes both protocols over the same `--grpclisten` address. The server determines which protocol to use based on the incoming
HTTP headers. It accepts `application/grpc-web` and `application/grpc-web-text`, over HTTP/1.1 and HTTP/2. The WebSocket
transport of gRPC-Web is not enabled.

## Connecting from a browser

BCHD only serves gRPC over TLS, so the browser must trust its certificate. The `rpc.cert` that BCHD makes is self signed
and only valid for the host names and addresses it was made for. Either trust `rpc.cert` locally (import it as a
certificate authority in the browser or operating system), run BCHD with a certificate from a public CA through
`--rpccert` and `--rpckey`, or put a reverse proxy with such a certificate in front of BCHD (see [NGINX](./nginx.md)).

BCHD answers the CORS preflight of a gRPC-Web call from any origin, for the paths of its own methods, when the
preflight asks for the `x-grpc-web` header, which gRPC-Web clients send. It allows any request header and credentials,
lets the browser cache the preflight for 10 minutes and exposes `grpc-status` and `grpc-message` on the response.
So any web page can call a public BCHD. When the node runs with `--grpcauthtoken`, send the token in the
`AuthenticationToken` header; a token in a web page is visible to its users.

## Streaming

The one major difference from a client perspective is gRPC-Web does not support bi-directional streaming. This
means that the `SubscribeTransactionStream` RPC cannot be used by the browser. Instead the server provides a `SubscribeTransactions`
RPC with the same functionality, but only using server side streaming. When using this endpoint you'll need
to close and re-open the stream every time you want to update your `TransactionFilter`.

All other calls work over gRPC-Web: the unary calls and the server streams `SubscribeTransactions`, `SubscribeBlocks`
and `SubscribeDoubleSpendProofs`.

## Client libraries

* [Connect-ES](https://connectrpc.com/docs/web/getting-started): `@connectrpc/connect-web` with `createGrpcWebTransport`
  and `@bufbuild/protobuf`, with code generated from `bchrpc.proto` by `@bufbuild/protoc-gen-es`, for example through
  [buf](https://buf.build/docs/). It runs in browsers and in Node.js. See the [web-connect](./client-usage-examples/web-connect)
  example.
* Google's [grpc-web](https://www.npmjs.com/package/grpc-web), with code generated by `protoc-gen-grpc-web`. It supports
  both JavaScript and TypeScript. Server streams need `mode=grpcwebtext`.
* The BCH specific `grpc-bchrpc-web` and `grpc-bchrpc-node` packages are unmaintained: both were last published in 2022,
  `grpc-bchrpc-web` is built on `@improbable-eng/grpc-web`, which is in maintenance mode, and `grpc-bchrpc-node` on the
  deprecated `grpc` package.
